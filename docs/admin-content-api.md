# Права публикации, отзыв доступа и изменение переводов

Создание `published`, редактирование или удаление уже опубликованной страницы/поста требуют одновременно `*:write` и `*:publish`. Для Admin API эти разрешения должны присутствовать у пользователя и в scopes Personal Access Token. `superadmin` не обходит ограничения scopes токена. Автор без права публикации может редактировать черновик; опубликованный материал открывается в режиме чтения. Публикацию и расписание выполняют отдельные действия, доступные владельцу права публикации. Дублирование создает новый черновик.

`PATCH /api/admin/v1/pages/{id}` и `PATCH /api/admin/v1/posts/{id}` объединяют переданные поля с сохраненными данными. Можно передать только `status`, отдельное поле перевода или отдельную локаль. Остальные переводы, содержимое, SEO и `custom_head_html` сохраняются. Новому переводу нужны `locale`, `title` и `slug`.

Смена статуса, отменяющая действующее расписание, тоже требует права публикации и `*:publish` scope токена. Редактирование черновика или запланированного материала без смены статуса сохраняет расписание и требует обычного права записи.

```json
{
  "translations": [{ "locale": "ru", "title": "Новое название" }],
  "remove_translations": ["en"]
}
```

`remove_translations` явно удаляет указанные локали. Нельзя одновременно удалить и обновить локаль или удалить последний перевод. Некорректное обновление откатывается целиком. Новые raw HTML head/custom code допускаются только advanced roles; PATCH не дает обычному автору менять сохраненный custom code.

`PUT` остается полной заменой набора переводов: нужно передавать все нужные локали и все поля каждого перевода. Неуказанные локали удаляются. Веб-формы тоже сохраняют полный набор. Для частичного обновления используйте PATCH.

Блокировка через изменение статуса или полный профиль, изменение ролей и пароля увеличивают `users.auth_version`, отзывают PAT и меняют remember token. Database sessions удаляются; file/Redis/cookie/array sessions отсекаются по несовпадению версии на следующем запросе. Снятие блокировки не восстанавливает старые сессии и токены. При самостоятельной смене пароля текущая браузерная сессия получает новую версию, остальные отзываются.

При обновлении необходимо применить миграцию `2026_10_01_000100_add_auth_version_to_users`. Старые браузерные сессии без отметки версии потребуют повторного входа; данные пользователей сохраняются. Корректность HTTP middleware не зависит от возможности физически удалить файл или Redis session.

## Категории

Категории используют общий сервис для web/API. `PUT /api/admin/v1/categories/{id}` заменяет набор переводов; `PATCH` объединяет поля по локали. Для существующего перевода можно передать только изменяемое поле. Новый перевод требует `locale`, `title`, `slug`. `remove_translations` доступен только для PATCH; нельзя одновременно обновлять и удалять локаль или удалять последний перевод.

Неуказанные поля PATCH сохраняются. `parent_id: null`, `cover_asset_id: null` и null в nullable metadata очищают значения; `is_active: false` деактивирует категорию. Полная веб-форма удаляет полностью очищенную дополнительную локаль и требует default locale. Не отображаемые в форме API-only robots/structured data сохранённого перевода сохраняются.

Slug уникален внутри локали. Конфликт возвращает validation error вместо 500; неизменённый slug текущей категории разрешён. Родитель не может быть категорией самой себе или её потомком. Изменения дерева сериализуются через `cms_mutation_guards`; родитель и актуальная цепочка проверяются внутри транзакции. `php artisan cms:categories:check` проверяет существующие циклы без изменения данных и возвращает ненулевой код при наличии циклов. Удаление категории сохраняет посты, убирает pivot associations и делает дочерние категории корневыми.

## Удаление медиа

`DELETE /api/admin/v1/assets/{id}` требует `assets:write`. Используемое медиа возвращает 409 `asset_in_use` и `usages`: тип/ID сущности, локаль, поле и ссылка на админку. Проверяются FK, вложенные блоки, HTML/Markdown, custom code, текущие темы/chrome и шаблоны. Исторические revisions не блокируют. Force-удаления нет. Web показывает те же использования.

При нескольких записях с одинаковыми `disk/storage_path` физический файл сохраняется до удаления последнего владельца. Ошибка очистки до DB commit возвращает 503 `asset_storage_cleanup_failed`: запись сохраняется, операция допускает повтор. Отсутствующий файл допускает идемпотентное удаление записи. Symlink/path traversal за пределы диска запрещены. Для приватного `local` disk удаление ограничено `assets/*`; ранее вручную зарегистрированные внутренние private paths требуют операторской обработки и не удаляются через CMS.

Local media перед удалением записи перемещается на том же filesystem в приватный карантин. Перед перемещением атомарно сохраняется журнал `storage/app/private/asset-deletions` (каталог 0700, JSON/bytes 0600). При откате запись и байты восстанавливаются. Для remote disks используется приватная backup copy перед удалением источника; это проверено с mock S3, не является доказательством работы любой S3-конфигурации. При аварии выполните `php artisan cms:assets:recover`: существующий владелец восстанавливает оригинал, успешно удалённый последний владелец очищает карантин. Повреждённый журнал или конфликтующий восстановленный путь требуют внимания оператора; существующие bytes не перезаписываются.

Если приватный purge после успешного DB commit не удался, API возвращает 503 `asset_storage_cleanup_failed` и сообщает, что публичный файл/запись уже удалены, а приватная очистка требует `cms:assets:recover`. Журнал остаётся для повторной recovery. До commit ошибка сохраняет запись; после commit восстановление не создаёт её заново. Завершённые JSON tombstones сохраняются, чтобы новые ссылки не возвращали удалённый путь. Повторная загрузка существующего файла на этот путь позволяет его использовать вновь. Legacy unregistered URLs, которых нет в deletion journals, не запрещаются.

## LLM drafts

LLM provider contract `generate(): array` сохраняется. Ответ API содержит прежний raw `generation.output` и отдельный нормализованный `generation.text`. OpenAI Responses извлекается из всех message/output_text blocks; Anthropic — из всех text blocks. Reasoning/tool blocks не попадают в draft, сериализация JSON вместо текста отсутствует.

Unsupported locale/provider, превышение входного лимита и отсутствие права/токен-scope записи проверяются до provider HTTP call. При `save_as_draft` omitted/null/true нужны одновременно `llm:generate` и соответствующие `pages:write`/`posts:write` у пользователя и PAT. При false достаточно LLM permission/scope; ответ сохраняет status 201 и `draft: null`. Locale omission/null использует default, supplied locale нормализуется lowercase/trim и проверяется по supported locales.

Пустой, refused, incomplete/truncated, malformed или oversized output возвращает 422 с стабильным `error_code` и `generation_id`, если он создан. Черновик не создаётся, exception/provider детали клиенту не выдаются. Автоматических платных retry и публикации нет. `llm.max_input_chars`/`llm.max_output_chars` применяются; превышение output limit не приводит к молчаливой обрезке. Успешный draft сохраняется через обычные content services с транзакцией, permission recheck, revision и инвалидацией cache; generated text экранируется.

При обновлении примените миграцию `2026_10_02_000100_create_content_mutation_guards` перед запуском новых writers. Все штатные writers используют media mutex; обход сервисов прямым SQL не участвует в гарантиях синхронизации.
