# TestoCMS — полный аудит рабочего цикла

Проверка начата 30 сентября и завершена 1 октября 2026 года, Asia/Vladivostok. Проверяемый commit: `3f6f1b463542b1311e1990fb64b645b87c8c02f9`.

## Вывод

**CMS проходит базовый цикл создания и ручной публикации, но полный цикл установки, эксплуатации и публикации работает некорректно.** Три сабагента выявили **43 подтверждённых дефекта: 18 P1 и 25 P2**. Дополнительно сохранены непроверенные риски и браузерное наблюдение; они не включены в это число. P0 в проверенной области не установлен. Это функциональное ревью, не сертификация безопасности.

Наиболее существенны блокеры чистой установки и VPS initialization, неправильное восстановление PostgreSQL, обход права публикации, потеря переводов, сохранение доступа заблокированных пользователей, нарушение сроков публикации и выдача снятого/удалённого контента из кеша. Поэтому готовность CMS к полноценной эксплуатации по заявленным сценариям не подтверждена.

Проходящие штатные тесты не противоречат этим находкам: они преимущественно проверяют изолированные операции, а дефекты возникают на переходах между установкой, изменением БД, сохранением HTML и повторным публичным запросом.

Ранее существовавший untracked файл `testocms` не трогали.

## Браузерная проверка рабочего цикла

Среда: отдельная копия `/private/tmp/testocms-audit-root`, SQLite файл, `http://127.0.0.1:8765`, отдельный администратор, локальная сборка с выполненными migrations/seeds и installed marker. Браузер Codex In-app Browser, окно 1280×720. Чистая установка этим не доказана: её отдельно проверял deployment-агент и выявил блокер DEP-01.

1. Открыта форма `/admin/login`; вход тестовым администратором приводит к панели.
2. Проверены **13 разделов**: Панель, Страницы, Посты, Шаблоны, Категории, Пользователи, Файлы, Тема, Обновления, API, Модули, Настройки, Аудит. У всех корректные URL/title и содержательный DOM, relevant console errors/warnings не зарегистрированы. Это smoke загрузки, не проверка каждой кнопки в каждом разделе.
3. Создана RU-страница `audit-cycle`: title/slug → fullscreen builder → heading block → изменение текста → «Сохранить и опубликовать» → серверный статус published и публичный контент виден.
4. После повторного открытия редактора сохранённый блок сохранён. Stage показывает пользовательский heading, а публичная страница дополнительно выводит большой демо-hero CMS, которого не было в сцене — **PUB-17**.
5. Создан RU-пост `audit-post`: title/slug → Markdown → текст с heading/bold → published → «Создать пост». В редакторе и на публичном URL текст правильно преобразован в HTML, console errors не зарегистрированы.
6. На странице «Действия» → «Вернуть в черновик»: flash `Page moved to draft.`, публичный URL после reload возвращает экран 404. Основная операция ручного снятия работает в данном сценарии.
7. На RU-only странице/посте присутствует EN-ссылка к отсутствующему переводу; отдельные runtime probes доказывают 404 при неправильном slug — **PUB-11**.

Публичные страницы открывались в том же browser profile, что и админка. Гостевые cache-hit и preview-expiry сценарии проверялись отдельными HTTP probes, а не этим браузерным smoke.

### Дополнительное браузерное наблюдение: статус формы после unpublish

В описанном цикле после возврата в draft и отказа от восстановления autosave HTML option имел `draft selected`, badge показывал draft, но фактическое значение `#page-status.value` оставалось `published`. Обычное «Сохранить изменения» без намеренного выбора статуса повторно опубликовало страницу (public 404 → 200). Это подтверждённое наблюдаемое поведение одного браузерного сеанса; точная причина и воспроизводимость в другом браузере ещё не установлены, поэтому оно **не включено в 43 дефекта**.

Связанные места: `resources/views/admin/pages/form.blade.php:1300`, `resources/js/admin/editors/pages/page-form.js:2622` и `:2772`, `PageCrudController.php:196`. Требуется проверить native form restoration, autosave recovery и flags `content_saved` при workflow actions. Перед обычным сохранением форма должна отображать и отправлять актуальный серверный статус; восстановление старого контента не должно незаметно восстанавливать публикацию.

## Порядок исправлений и критерии приёмки

1. **Установка и сохранность данных:** DEP-01/02/03/04/06/11, ADM-03. Чистая установка без `.env`/marker/таблиц, upload после установки, официальный подписанный ZIP, искусственно неудачное обновление и сравнение полного schema/content после rollback. На MySQL и PostgreSQL проверять отдельно.
2. **Права и публичная видимость:** ADM-01/02, PUB-01/05/07/08. Negative role/token tests, немедленная блокировка session/PAT, каждый public detail использует одинаковое live predicate, preview проверяет срок на каждом запросе, заголовки защиты одинаковы на MISS/HIT.
3. **Единый workflow:** PUB-02/03/04/09. Отложенная операция отдельно от actual status; перенос/отмена заменяют pending task; due command и HTTP fallback очищают все связанные cache keys. После task проверять и БД, и повторный гостевой HTML/API/SEO запрос.
4. **Свежесть динамического контента:** PUB-06 и ADM-04/09. Сохранить page с post_listing → снять/изменить post → проверить страницу после flush; physical cleanup одинаков для web/API; PATCH не уничтожает несообщённые поля/переводы.
5. **Остальная функциональность:** корректные locale switch/pagination/filtering, categories graph/validation/null, RSS XML, conditional validators, SQLite body search, LLM raw response parser и допустимые locales.
6. **Соответствие интерфейса результату:** убрать демо-hero из всех пользовательских страниц, согласовать stage/public templates, повторить UX статус/автосохранение после workflow actions. Пройти upload/image picker, move/delete block, revision restore, responsive views и keyboard flows.
7. **Эксплуатация:** writable module directories, сохранение env integrations, atomic redo, корректные shell credentials, рестарты workers после update, фактический cron/queue на production профиле.

Завершение исправлений принимается по повторению исходных ошибочных сценариев с правильными expectations. Проходящий probe, который утверждает «ошибка 500 присутствует», не является регрессионным тестом правильного поведения: assertions нужно изменить после исправления.

## Непроверенные области

Полный current Docker image rebuild/stack, реальный shared hosting и публичный production домен, MySQL, Redis, CDN/reverse proxy, PHP 8.2–8.4, настоящие cron/long-running queue workers, нагрузка/конкурентность scheduler, live LLM и сторонние embeds, все кнопки/виджеты/блоки во всех viewports, WCAG проверка screen reader и полноценный security audit. Нет оснований утверждать, что «все элементы CMS работают».

Отдельные риски в профильных отчётах: timezone schedule UX, конкурентное двойное исполнение задач, API-only fallback без cron, categories noindex/canonical, устаревшие module_widget HTML, неполный database backup при restricted proc_open, version metadata и кеши persistent Docker volumes. Они не включены в 43 подтверждённых дефекта.
