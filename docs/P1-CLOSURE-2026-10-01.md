# TestoCMS: выполнение плана закрытия 18 P1

Дата: 1 октября 2026. Исходное состояние: `3f6f1b463542b1311e1990fb64b645b87c8c02f9`. Отчёт дополняет [исторический аудит](CMS-AUDIT-2026-09-30.md); остальные 25 P2 не считаются закрытыми.

## Результат и границы проверки

Реализованы все пять пакетов плана: установка/медиа, updater/backup, доступ/переводы, публичная выдача/кеши, расписания. Статусы ниже относятся к воспроизведениям в указанных тестовых окружениях, а не к уже состоявшемуся production rollout. Полная приёмка каждой комбинации PHP/СУБД/cache/session остаётся отдельным release gate.

Все разрушительные сценарии обновления и восстановления выполнялись в `/private/tmp` и disposable БД. Рабочий `.env` не изменён; рабочая CMS не обновлялась. В ходе работы два обычных PHPUnit запуска ошибочно использовали cwd репозитория: они использовали SQLite `:memory:` и тестовые fixtures/framework caches, не пользовательскую БД. Последующие проверки проводились в изолированных копиях.

## Архитектурные контракты

- `remove_translations: ["en"]` разрешён для PATCH страниц/постов. Нельзя одновременно обновить и удалить одну локаль; необходим хотя бы один валидный перевод. PUT и полные web формы заменяют набор. См. [API контракт](admin-content-api.md).
- Admin detail возвращает `scheduled_actions`. DELETE `/api/admin/v1/{pages|posts}/{id}/schedules/{schedule}` проверяет принадлежность и publish capability.
- `cms:schedules:check` — read-only, ненулевой exit при противоречиях с ID. До DDL миграция выбирает последнее задание/action по created_at,id, отменяет дубли; конфликтное окно блокирует migration. Старое unpublish-only scheduled автоматически не публикуется.
- Public generation UUID сохраняется в БД вместе с изменениями; cache failures дают uncached response. Запрос фиксирует generation до чтения, поздняя запись остаётся в старом namespace. При rollback generation не переиспользует пространство будущего содержимого.
- Schedule service использует entity→schedule lock и повторную проверку pending; ручное publish сохраняет unpublish, draft/archive/delete отменяют обе задачи. См. [правила публикации](publication-safety.md).

## Установка и переход установленной CMS

Shared hosting использует [HTTP мастер](shared-hosting-deploy.md). VPS использует [readonly env и initialization service](docker-vps.md). Команда `cms:setup --from-env --no-interaction` не меняет env и существующий пароль admin. Не переносите storage/installed, приватные runtime файлы и старый physical public/storage в Docker image.

Для старого parser обязателен промежуточный пакет. Он содержит полный baseline tree с обновлённым updater/bootstrap, старые миграции без добавления новых, совместимые `php:^8.2.0` и числовой `cms_from:1.0.0`. Частичная упаковка только app/Updates недопустима: старый applier заменяет top-level каталоги целиком.

1. Сделать отдельный проверенный backup БД и кода **до bridge**. Остановить queue/scheduler и дождаться завершения writers до запуска старого updater: его процессы ещё не участвуют в новом flock gate. Исходный updater PostgreSQL не обеспечивает безопасного полного отката. SQLite файл должен находиться вне заменяемых code directories, например в storage/app/private, а не database/.
2. В исходном env задать `CMS_UPDATE_HEALTH_URL=https://your-site/up` (без redirect). Проверить200.
3. Подписать bridge реальным release ключом через `scripts/build-updater-bridge.php --base-ref=<audited-baseline> --version=<target>-rc.1 --out=<zip>` после frontend build. `--assets-root` допускает уже собранный Vite каталог. Проверить `scripts/verify-release-package.php <zip> <zip>.sig`.
4. Применить bridge, перезапустить PHP/queue процессы, проверить fresh boot и `/up`.
5. Исправить конфликтующие расписания до основного пакета; его preflight проверяет старую схему read-only. На PG подготовить требования ниже. Применить основной подписанный пакет с миграциями.
6. Старые web sessions без auth_version требуют повторного входа. Заблокированные пользователи после unblock входят заново и получают новые PAT.

Локальный bridge fixture подписан одноразовым **тестовым** ключом; не является официальной поставкой. Production подпись используется только release workflow через secret `CMS_UPDATE_PRIVATE_KEY`. CI baseline pin задаётся `CMS_UPDATER_BRIDGE_BASE_REF`, по умолчанию audit commit выше. Перед будущими версиями baseline необходимо заново проверить.

## PostgreSQL backup/recovery

Только выделенная CMS база: `CMS_UPDATE_PGSQL_DEDICATED_DATABASE=true`, `CMS_UPDATE_PGSQL_MAINTENANCE_DATABASE=postgres`. Роль должна владеть базой, иметь CREATEDB и доступ к служебной базе; инструменты pg_dump/pg_restore/psql — совместимой проверенной major версии (VPS закреплён на16). Это декларация оператора о выделенной базе: автоматически доказать отсутствие внешних клиентов или чужих данных невозможно.

После maintenance exclusive gate ждёт завершения web mutations, очереди и scheduler/fallback. Все контейнеры должны разделять storage/private и POSIX flock. Custom backup сначала пробно восстанавливается в staging DB; проверяется schema digest, все user table rows и sequence values. Legacy SQL восстанавливается транзакционно с ON_ERROR_STOP; custom archive — с `--single-transaction --exit-on-error`, согласно [pg_restore16](https://www.postgresql.org/docs/16/app-pgrestore.html). Код и dump проверяются по checksum до замены.

Rename выполняется через maintenance connection, соединения целевой базы прекращаются. Переименование через отдельное соединение и требования owner/CREATEDB соответствуют [ALTER DATABASE16](https://www.postgresql.org/docs/16/sql-alterdatabase.html). Два rename не атомарны: operation.json фиксирует этапы и позволяет продолжить переключение или вернуть исходное имя после сбоя. Старую БД сохраняем с ALLOW_CONNECTIONS=false. После успешного recovery и операторской проверки retained базу можно удалить через maintenance connection; автоматическое удаление не выполняется. Ротация backup files не удаляет retained базы.

Не снимать maintenance вручную после неудачного restore. `php artisan cms:updates:recover <backup_key>` читает private manifest/journal даже когда backup record отсутствует в восстановленной БД. `health_unverified` оставляет maintenance включённым; после исправления URL/связности повторить recovery и получить verified success. Журналы и ошибки находятся вне восстанавливаемой БД в storage/app/private/core_updates/backups/<key>/operation.json.

## Проверки и доказательства

Общий PHPUnit: **296 тестов / 1613 assertions**, PASS на PHP8.5.3/SQLite. Полный PHPStan — PASS без новых baseline подавлений; удалены устаревшие suppressions. Frontend — PASS,53 modules (только предупреждение stale Browserslist). Pint — PASS; исторические negative probes исключены из форматирования, правильное поведение проверяют новые regression tests.

Отдельный PostgreSQL16 integration: **5 tests / 44 assertions PASS**. Проверены данные, схема, sequences, migrations, отсутствие добавленных обновлением объектов, повреждённый plain SQL, interruption между rename. Дополнительно проверены отказ до backup для non-owner/CREATEDB и owner/NOCREATEDB, неизменность данных, завершение активного подключения и смена DB OID при сохранении исходной базы.

Браузерный цикл выполнялся на fresh disposable VPS: login → RU/EN Markdown draft → preview → published URL → future unpublish → reschedule (history cancelled old task, current status published). Браузер выявил вложенную форму DELETE отмены внутри editor form, из-за которой Save удалял disposable post: дефект исправлен выносом cancel forms за пределы editor. DOM regression проверяет PUT и DELETE отдельно на обеих страницах; повторный browser Save сохранил пост #2 в draft, отменил задание с причиной manual-draft и вернул404 на публичном URL. Полный browser update→rollback не выдаётся за выполненный: update/recovery проверяются отдельно реальными сервисами/HTTP и PG integration.

CI дополнен PHP8.2–8.5, PG16 destructive opt-in job, MySQL8 targeted suite и проверкой настоящего signed ZIP. GitHub Actions/официальная release подпись и production rollout в этой сессии не запускались. Проверка всех комбинаций PHP8.2/8.3/8.4/8.5 × MySQL/PG × file/Redis session/cache полностью локально не выполнена; CI outcomes нужны для окончательной release приёмки.

Артефакты: [JUnit](p1-verification-2026-10-01/phpunit.xml), [PHPUnit](p1-verification-2026-10-01/phpunit.log), [PHPStan](p1-verification-2026-10-01/phpstan.log), [frontend](p1-verification-2026-10-01/frontend.log), [Pint](p1-verification-2026-10-01/pint.log). Тестовые signing keys и env credentials не включены.

## Итоговая приёмка

17 P1 закрыты по обязательным локальным воспроизведениям и regression tests в перечисленных окружениях. DEP-03 реализован и проверен на реальных тестово подписанных ZIP, включая применение bridge исходной CMS; строгий критерий официального ZIP из release pipeline ещё требует запуска GitHub Actions с production signing secret. Поэтому DEP-03 не помечен окончательно закрытым. Полная PHP8.2–8.5 матрица и production rollout остаются release gates; исходники, автоматические проверки и операционные инструкции для них подготовлены.

**Docker ограничения:** полный production Dockerfile build прошёл до последних изменений helper/pin16. Последующий latest-source image поверх нового production runtime с client16 прошёл и использовался для fresh VPS smoke, но окончательный canonical Dockerfile после pin16 требует полного CI/release rebuild. Это зафиксировано в [Docker evidence](../docker/smoke/evidence-2026-10-01.md). [Cold VPS](p1-verification/deployment-vps-cold.json), [repeat](p1-verification/deployment-vps-repeat.json), [media overwrite](p1-verification/deployment-vps-overwrite.json), [Apache](p1-verification/deployment-apache-smoke.json).

Очистка: собственные MySQL/Redis/VPS/Apache/PG контейнеры и volumes удалены, собственные HTTP servers остановлены; signing fixture seed удалён. Пользовательские Docker ресурсы не удалялись. `.env` рабочей CMS сохранил исходную дату изменения. Исходники не закоммичены и релиз не опубликован.
